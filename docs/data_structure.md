# tea_assistant — Data Structure

## Общий принцип
В первой версии проекта данные хранятся в **JSON-файлах**. Основной источник — `teas.json`.

Структура должна быть простой, читаемой и удобной для ручного редактирования. Все поля должны быть нормализованы и использовать единый стиль значений.

## Основной файл данных
Рекомендуемый путь:
- `public/teas.json`

Формат:
- массив объектов;
- каждый объект = одна карточка чая.

---

## Структура объекта Tea

Ниже перечислены рекомендуемые поля.

### Обязательные поля

#### `id`
- Тип: `string`
- Уникальный внутренний идентификатор записи.
- Пример: `"tea-001"`

#### `article`
- Тип: `string`
- Артикул товара.
- Пример: `"PU001"`

#### `name`
- Тип: `string`
- Название чая.
- Пример: `"Шу Пуэр Черносливовый"`

#### `category`
- Тип: `string`
- Основная категория чая.
- Примеры:
  - `"пуэр"`
  - `"зеленый"`
  - `"улун"`

#### `type`
- Тип: `string`
- Более точный тип внутри категории.
- Примеры:
  - `"шу"`
  - `"шен"`
  - `"сырой"`
  - `"выдержанный"`

#### `teaClass`
- Тип: `string`
- Класс / уровень чая.
- Примеры:
  - `"стандартный"`
  - `"купаж"`
  - `"элитный"`

#### `description`
- Тип: `string`
- Короткое понятное описание чая в 1–3 предложениях.

#### `taste`
- Тип: `string[]`
- Основные вкусовые характеристики.
- Примеры значений:
  - `"плотный"`
  - `"мягкий"`
  - `"сухофруктовый"`
  - `"древесный"`
  - `"ореховый"`
  - `"сладковатый"`

#### `aroma`
- Тип: `string[]`
- Основные ароматические характеристики.

#### `effect`
- Тип: `string[]`
- Эффект / ощущение от чая.
- Примеры:
  - `"бодрит"`
  - `"мягко тонизирует"`
  - `"собирает"`
  - `"расслабляет"`

#### `bestTime`
- Тип: `string[]`
- Когда лучше пить чай.
- Примеры:
  - `"утро"`
  - `"день"`
  - `"ранний вечер"`

#### `brewingMethods`
- Тип: `string[]`
- Подходящие способы заваривания.
- Примеры:
  - `"пролив"`
  - `"термос"`
  - `"чайник"`
  - `"кружка"`

#### `brewingGuide`
- Тип: `object`
- Краткие инструкции по завариванию по способам.

Рекомендуемая структура:
```json
{
  "proliv": "Короткие проливы, чтобы раскрыть вкус постепенно.",
  "thermos": "Использовать умеренную дозировку, чтобы чай не стал слишком тяжелым.",
  "teapot": "Подходит для повседневного заваривания средней крепости."
}
```

#### `tags`
- Тип: `string[]`
- Ключевые теги для поиска, фильтрации и подбора.
- Примеры:
  - `"плотный"`
  - `"без землистости"`
  - `"новичку"`
  - `"для термоса"`
  - `"на каждый день"`

#### `antiTags`
- Тип: `string[]`
- Нежелательные или исключающие признаки.
- Примеры:
  - `"землистый"`
  - `"резкий"`
  - `"дымный"`
  - `"горький"`

#### `forBeginners`
- Тип: `boolean`
- Подходит ли чай новичку.

#### `forThermos`
- Тип: `boolean`
- Подходит ли чай для заваривания в термосе.

#### `forProliv`
- Тип: `boolean`
- Подходит ли чай для проливов.

#### `alternatives`
- Тип: `string[]`
- Список `id` похожих чаев.
- Используется для блока альтернатив.

---

## Рекомендуемые дополнительные поля

#### `clientProfile`
- Тип: `string[]`
- Для какого типа клиента подходит чай.
- Примеры:
  - `"новичок"`
  - `"опытный"`
  - `"на каждый день"`
  - `"для знакомства"`

#### `avoidFor`
- Тип: `string[]`
- Кому не стоит рекомендовать чай.
- Примеры:
  - `"тем, кто не любит землистость"`
  - `"новичкам"`
  - `"тем, кто ищет мягкий чай"`

#### `notes`
- Тип: `string`
- Дополнительные внутренние примечания для продавца.

#### `isActive`
- Тип: `boolean`
- Активна ли позиция в выдаче.
- Если товара временно нет, можно скрывать из рекомендаций.

#### `sortOrder`
- Тип: `number`
- Ручной приоритет сортировки в списках.

## Требования к значениям

### 1. Единый словарь
Для тегов, антитегов, способов заваривания и клиентских сценариев нужно использовать заранее согласованный словарь значений.

Например:
- использовать всегда `"термос"`, а не вперемешку `"в термос"`, `"термосом"`, `"для термоса"`;
- использовать всегда `"пролив"`, а не `"гунфу"` в одной записи и `"проливы"` в другой, если это не разделяется отдельно.

### 2. Без дублирования смысла
Если признак уже отражен в `forBeginners`, не нужно пять раз повторять его в несистемной форме в разных текстовых полях.

### 3. Читаемые тексты
`description`, `notes`, `avoidFor` и `brewingGuide` должны быть написаны простым понятным языком, удобным для сотрудника.

## Дополнительные файлы данных
При необходимости позже можно добавить:

### `matrix.json`
Матрица соответствия для логики рекомендаций.

### `tag_dictionary.json`
Словарь нормализованных тегов и синонимов.

### `ai_prompt_config.json`
Подсказки и правила для AI-разбора текста.

На старте эти данные могут быть описаны в markdown-документах или встроены в код.

## Вывод
Минимальный рабочий набор данных для MVP строится вокруг одной сущности — `Tea`. Структура должна поддерживать:
- быстрый поиск;
- фильтрацию;
- ранжирование;
- показ карточки;
- рекомендации;
- дальнейшее расширение проекта без полной переработки данных.
