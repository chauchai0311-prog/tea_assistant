# tea_assistant — Recommendation Logic

## Общий принцип
Логика рекомендаций в `tea_assistant` строится не на генерации ответа AI-моделью, а на заранее определенных данных и правилах.

Основа подбора:
1. данные карточек чаев;
2. теги и антитеги;
3. матрица соответствия;
4. scoring / ранжирование.

AI используется только для того, чтобы перевести свободный текст сотрудника в структурированный набор параметров.

---

## Цель рекомендательного механизма
На входе система получает:
- запрос клиента в виде фильтров или свободного текста;
- дополнительные условия использования;
- ограничения и исключения.

На выходе система должна возвращать:
- **основной рекомендованный чай**;
- **1–2 альтернативы**;
- краткое объяснение, почему вариант подходит.

---

## Источники входных данных

### 1. Ручные фильтры
Сотрудник может выбрать напрямую:
- вкусовые параметры;
- нежелательные параметры;
- уровень клиента;
- способ заваривания;
- время употребления;
- тип чая.

### 2. Свободный текст
Сотрудник может написать запрос естественным языком.

Пример:
> Клиент хочет плотный чай без землистости, для термоса, новичку.

AI должен вернуть структуру, например:
```json
{
  "includeTags": ["плотный"],
  "excludeTags": ["землистый"],
  "forBeginners": true,
  "brewMethod": "термос"
}
```

После этого применяется обычная логика рекомендаций.

---

## Базовая модель отбора
Каждый чай проходит через три стадии:

### 1. Первичная фильтрация
Из выборки исключаются чаи, которые явно не подходят по жестким условиям.

Примеры жестких условий:
- если выбран способ `термос`, а `forThermos = false`, чай исключается;
- если нужен чай для новичка, а чай явно не подходит новичкам, он опускается или исключается;
- если чай неактивен (`isActive = false`), он не показывается;
- если указан тип чая, сначала показываются только совпадающие категории.

### 2. Подсчет совпадений
Для оставшихся чаев считается score.

### 3. Финальная выдача
Список сортируется по score. Система показывает:
- лучший вариант;
- 1–2 следующих варианта как альтернативы.

---

## Рекомендуемая схема scoring
Ниже — базовая схема, которую можно скорректировать после тестирования.

### Положительные баллы

#### Совпадение по тегам
- +3 за каждое точное совпадение из `includeTags`

#### Совпадение по вкусовому профилю
- +2 за совпадение по `taste`

#### Совпадение по аромату
- +1 за совпадение по `aroma`

#### Подходящий способ заваривания
- +2 если выбранный способ заваривания есть в `brewingMethods`
- +2 дополнительно если:
  - `forThermos = true` и выбран `термос`
  - `forProliv = true` и выбран `пролив`

#### Подходит новичку
- +2 если `forBeginners = true` и выбран сценарий новичка

#### Подходит по времени употребления
- +1 если `bestTime` совпадает с выбранным временем

#### Приоритет матрицы
- +2 / +3 если матрица явно усиливает этот чай или группу чаев под данный запрос

---

## Отрицательные баллы

#### Совпадение с нежелательными признаками
- -4 за каждое совпадение с `excludeTags`
- -4 если у чая есть нежелательный антитег из запроса клиента

#### Неподходящий профиль для новичка
- -3 если клиент новичок, а чай рекомендуется скорее опытному

#### Неподходящий способ заваривания
- -3 если способ возможен, но не является рекомендованным
- исключение, если способ строго запрещен правилами

#### Конфликт с матрицей
- -2 / -3 если матрица явно понижает чай для данного сценария

---

## Роль матрицы соответствия
Матрица — ключевой источник экспертной логики.

Она должна описывать:
- какие запросы клиента соответствуют каким тегам;
- какие признаки усиливают рекомендацию;
- какие признаки исключают варианты;
- какие категории или типы чая приоритетны;
- какие профили лучше для новичка;
- какие профили лучше для термоса;
- какие профили лучше для вдумчивого заваривания проливами.

### Пример логики матрицы
Запрос:
- `плотный`
- `без землистости`
- `новичок`
- `термос`

Матрица может задавать такую интерпретацию:
- усиливать теги: `плотный`, `мягкий`, `сухофруктовый`, `чистый профиль`
- исключать: `землистый`, `резкий`, `дымный`
- повышать чаи с `forThermos = true`
- повышать чаи с `forBeginners = true`
- понижать сложные и спорные выдержанные профили

---

## Приоритеты выдачи
Система не должна возвращать длинный список без структуры.

### Формат результата
1. **Основной вариант** — чай с наивысшим score
2. **Альтернатива 1** — близкий по профилю вариант
3. **Альтернатива 2** — второй резервный вариант

### Ограничение
Если после фильтрации осталось слишком много совпадений, нужно показывать только верхнюю часть рейтинга.

---

## Правила выбора альтернатив
Альтернативы могут формироваться двумя способами:

### Вариант A — по score
Берутся следующие позиции после лидера.

### Вариант B — по явным связям
Если у карточки есть поле `alternatives`, то приоритетно показываются они, если они не противоречат текущим условиям.

Рекомендуемый гибридный подход:
1. сначала основной вариант по score;
2. затем проверка `alternatives`;
3. если альтернативы валидны — показывать их;
4. если нет — брать следующие по score.

---

## Объяснение рекомендации
Для каждого результата нужно формировать короткое объяснение, а не просто показывать карточку.

### Объяснение должно учитывать:
- какие ключевые теги совпали;
- почему чай подходит под способ заваривания;
- подходит ли он новичку;
- какие нежелательные признаки удалось избежать.

### Пример шаблона
> Подходит, потому что дает плотный и мягкий профиль, не уходит в выраженную землистость и хорошо показывает себя в термосе.

Такое объяснение должно строиться по данным, а не выдумываться свободно.

---

## Поведение AI-слоя
AI подключается только к блоку свободного текстового ввода.

### Что делает AI:
- извлекает из текста параметры;
- приводит их к допустимым значениям системы;
- возвращает JSON фиксированной структуры.

### Что делает система после AI:
- применяет параметры к фильтрации;
- считает score;
- показывает рекомендации.

### Что AI не должен делать:
- выбирать чай вместо rules engine;
- ссылаться на отсутствующие данные;
- генерировать длинные экспертные описания без опоры на карточки.

---

## Обработка отсутствия точного совпадения
Если точного совпадения нет:
1. ослабить второстепенные условия;
2. сохранить обязательные ограничения;
3. показать ближайшие варианты;
4. отдельно обозначить, что это ближайшие альтернативы.

Пример:
- если нет варианта `без землистости`, но есть более чистый и мягкий профиль, показать его как компромисс.

---

## Правила для минимального MVP
На старте рекомендуется внедрить только простой набор правил:
- фильтрация по активным чаям;
- поиск по артикулу и названию;
- фильтрация по тегам;
- исключение по антитегам;
- учет новичка;
- учет способа заваривания;
- базовый score;
- топ-1 + 2 альтернативы.

Этого достаточно для первой работающей версии.

---

## Что можно улучшать позже
После тестов с сотрудниками можно добавлять:
- более точные веса score;
- сценарии по времени суток;
- разные режимы для новичка и опытного продавца;
- учет наличия товара;
- контекстные подсказки, что спросить дальше;
- обучение на истории запросов.

---

## Вывод
Рекомендательная логика `tea_assistant` должна быть:
- понятной;
- управляемой;
- предсказуемой;
- основанной на ваших данных и экспертной матрице.

AI в этой системе — вспомогательный слой для удобства ввода, но не центр принятия решений.
